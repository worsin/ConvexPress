# Canonical block contract

- Own content in `blocks/<namespace>/<name>/block.json`. Use stable names, closed fields, bounded inputs, useful defaults and representative examples. Read `scripts/blocks/schema.mjs` for the current vocabulary; generated JSON Schema alone cannot prove semantic constraints.
- Own the baseline renderer in the adjacent `render.tsx`, using `defineBlock` or the matching typed data-block factory and SDK primitives. Names, attrs and versions come from generated contracts. Do not add a second handwritten schema or registry entry.
- Canonical instances use `children`, `layout`, `anchor`, `visibility` and validated `treatment`/`style` where supported. Read `scripts/blocks/instance-runtime.mjs` for the exact closed envelope. Legacy `innerBlocks` is migration input, never new canonical output.
- The generic editor derives controls from fields. Dedicated editing adapters must still use generated validation and the revision-guarded canonical document service.
- Templates own presentation and token mapping. Content does not contain CSS, executable code, credentials or copied live prices. Packs do not inherit other packs. A generic SDK treatment is not evidence of a pack-owned treatment.
- Dynamic blocks declare resolvers and requirements. The backend owns authorization, site scope and allowlisted result DTOs. A declaration does not implement a resolver. Rendering rejects unknown data or missing requirements rather than inventing business data.
- Authoring validates bound dynamic arguments against the same resolver contracts and normalization used for rendering. Required source selections and integral counts must fail beside their bound editor fields, before save or preview. This is write-time validation, not permission to read a resource; existing stored values remain readable for repair and draft recovery. Do not duplicate resolver rules in individual forms. Reusable content references are separately expanded and revision-authorized before query planning.
- Declare searchable editorial copy with optional `searchText` paths in the canonical spec, for example `[["heading"], ["items", "*", "body"]]`. For plain-text fields rendered by the SDK Prose adapter, use `{ "path": ["body"], "format": "prose" }` to index displayed labels without Markdown link destinations. Literal text stays literal, and richtext is extracted from text nodes only. Paths must terminate at plain text or richtext; formatted IDs, references, links and containers are rejected. Omission means no search text, never automatic extraction of string attributes. Declare only visible authored copy, not private settings, action labels, remote query results or conditional alternatives. Search declarations do not authorize disclosure: current document, ancestor, membership, plugin and template gates still apply. Custom compositions and unsupported conditional fields require an explicit projection before becoming searchable.
- Persisted version changes require explicit, tested conversion through the canonical migration path. Preserve source revisions and refuse unsupported input. A `migrations.ts` file by itself is not wired into the canonical service.
- Keep client identities and resource references site-local. Pattern content must not ship database IDs; cross-site promotion requires validated mapping and scope checks.
- Generated code is output, not an authoring surface. Use `sync:blocks:all`; review generated diffs and run `check:blocks`.
- When older stored text fields represent an action, declare `authoringActions: [{ path: ["items", "*"], href: "url", label: "label" }]` on the spec. Paths select objects or object-repeater rows; `[]` selects root attrs. Destinations use the shared safe-link rules and need a nonblank visible label. Empty destinations permit text-only labels. These are write-time rules: `validateBlockAttrs` still reads old values for repair, while `validateBlockAuthoringAttrs` rejects invalid new edits. Server save/preview/publication and reusable-content writes enforce them independently of the editor. Draft recovery preserves historical values; publishing a recovered invalid action requires correction. Never silently sanitize saved content or change a storage version to hide a validation mismatch.
- Contract tests, renderer checks, native editor save/reload and public rendering prove different boundaries. Record each actually tested boundary. Screenshots or file existence alone do not prove full visual, interaction, accessibility or motion acceptance.
- If an action's renderer accepts fewer link types, set its optional `protocols` list to that exact policy, for example `["http", "https", "relative", "anchor"]` for a web-only collection action. Omission uses the shared safe-link policy, including email and telephone links. This restriction remains write-only; historical values can still be read and repaired.
- Declare `multiline: true` for short text fields that render prose with line breaks. This selects a textarea even for an empty initial value; it does not alter the stored string or its length limit. Do not rely on the editor detecting line breaks after a single-line input has already discarded them.
- An `icon` field may declare a bounded `options` list of supported kebab-case names. The generated editor then offers a selector and validators reject unsupported names. Choose names actually supplied by the Website icon primitive. Omitting `options` preserves the existing open-name contract; do not tighten an existing saved field without compatibility review. For an existing open-name icon, `optionsMode: "authoring"` retains the stored string schema but constrains save/preview/publication to the declared options. Unsupported historical values stay visible in the selector for explicit replacement or removal. This is enforced for Library and custom-composed content; examples and declared defaults must also satisfy the choices. Optional fields without defaults remain absent in old documents.

- A text field may declare `authoringNonblank: true` when supplied text must be visible (for example a badge label). This rejects whitespace-only or default-ignorable-only new values without trimming, rewriting or invalidating historical stored strings. Required/optional/nullability remain controlled by the existing field declaration. Examples and defaults must satisfy the write-time rule. Library and custom-composed save/preview/publication enforce it; historical draft recovery remains available.
- Object fields and object-repeater rows may declare `authoringConstraints` using the existing cross-field constraint vocabulary. Use this for write-time rules such as a schedule's `ordered` start/end dates when historical values must remain readable and recoverable. New edits, previews, publication, examples and defaults enforce the rule through shared validation; stored shape and version remain unchanged. Errors retain the full nested field path. `constraints` continues to enforce stored-shape rules.
