# Contact form — implementation in progress, September 6

The existing canonical Contact form spec carries inline fields, copy, a recipient and success text, but had no renderer or server submission path. Preserve inline authoring and use the existing Forms engine for backing records, validation, spam protection and native entries. This is not complete and is not deployed.

## Implemented now

- Canonical renderer: two-column copy/fields composition on wide screens, single column on mobile, pack-owned typography/colors/radii, visible labels and required indicators. Account-free preview has no form element or enabled submission control and omits the recipient address from HTML. No fake success state or callback is installed.
- Shared contactContracts parser reuses the generated block schema and adds field-name uniqueness/safety, labels, select option integrity and recipient validation. The exact source is mirrored into portable and deployed foundation closures.
- New contact.submission host capability keeps native insertion/public use gated while the submission integration is unfinished. Only the isolated BlockDemo and renderer fixture enable it. Forms plugin is required. This is an implemented-host capability, not a user RBAC grant.
- New internal authoring helper syncContactForm creates/reuses a Forms record for a post/block pair. Form IDs and field keys/IDs survive edits. Removed definitions move to an inactive history group and can be restored without dropping historical answer references. Reads use request budgets and bounded source traversal; ownership fields/index are additive. Individual helper-created Forms records remain draft. The document synchronizer activates backing forms in the same transaction as the canonical save, with current source authorization still denying draft/future/private pages. No notification/confirmation rows are created yet.

## September 6 — confirmation response authority prerequisite

While wiring the saved success message, confirmed an existing Forms disclosure path: resolveConfirmation accepted only formId/submissionId, loaded that submission's values and substituted merge tags without verifying the IDs belonged together or the caller held submission authority. Added a real registered-handler regression; it failed against the previous implementation.

- Successful completed submits now mint a 256-bit confirmation receipt, return it only to the caller, and store its SHA-256 hash plus a10-minute expiry. Partial saves do not grant confirmation access. Both direct and CAPTCHA-final submits use the same implementation.
- Public confirmation resolution checks token format/hash, exact form/submission relationship, completed status, expiry and current form publication/plugin/route/login/source-page access before reading configuration or answers. Contact source passwords are accepted at this boundary. Missing proof on older clients/entries is refused; existing UI catches failures and uses its generic thank-you fallback.
- Configuration/answer reads are streamed through the existing request ledger and the public result has an explicit return validator. The server never puts the bearer receipt in stored event metadata or public queries.
