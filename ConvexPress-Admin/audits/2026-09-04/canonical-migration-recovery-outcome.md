# Original-editor migration recovery source checkpoint

Root's live Care migration exposed a real gap: its original marked article was retained in a safety revision, but the revision UI reported it as unrestorable. Merely retaining the old bytes did not provide usable recovery. This checkpoint adds the actual recovery operation and its canonical undo; it does not claim root has deployed or accepted them yet.

`canonicalDocuments.recoverLegacy({postId, revisionId, expectedRevision})` restores a supported complete `snapshotVersion:2` legacy article/empty-editor safety snapshot to the original editor format. It preserves the original stored article bytes and all revisioned authoring fields, including layout, prompt, excerpt and header/footer settings, without reserializing the article into a newly converted tree. It keeps current routing, ownership, publication state, password and membership policy records. The block-format discriminator becomes explicit 1 and the CURRENT revision advances; it never reuses a historical revision number. Autosaves are cleared as part of the explicit reviewed recovery.

Before recovery the service rechecks editorial access, restore capability and publish capability for non-drafts, exact current canonical revision, snapshot parent/type, complete snapshot version, supported historical content model, stored size and media attachment availability. The current canonical authoring state is saved as an undo snapshot in the same transaction. The media guard accepts the downgrade only with a distinct source-internal one-use permit bound to the exact v2 previous state and exact v1 patch. Legacy writers, forged permits, altered patches, reused receipts and unrelated-table operations cannot downgrade canonical content.

The recovery receipt is a separate closed contract: `{postId, revision, blocksVersion:1, authoringDigest}`. Native consumers must verify the next authorized legacy get against this complete source digest before reopening the original editor. Revision rows add optional `action: 'restore-canonical'|'recover-legacy'|null`; the new server emits the actionable value and consistent restorable/reason fields. Existing clients may still omit action. Supported legacy recovery actions are offered while the current document is canonical; after recovery the normal legacy editor owns legacy restoration and this history exposes canonical undo.

The existing canonical `restore` also accepts `expectedAuthoringDigest`. It is mandatory when the current document is legacy, alongside exact revision. This prevents overwriting a legacy article edit or autosave that did not advance its block revision. Restoring the saved canonical snapshot validates its generated tree and current data/media/presentation, snapshots the current original-format document, advances revision again, and retains current publication/access settings. Authorized legacy get already returns source digest/revision for draft, published, scheduled and private documents, so recovery does not require a new bearer, preview token or an authority bypass.

Supported recovery currently covers complete original article/empty-editor snapshots whose authoring model can be validated by the implemented lossless migration adapter. Historical legacy block trees, page sections, structured blog bodies and incomplete old snapshot versions still require their reviewed adapters. They remain explicit unsupported history rather than being flattened, partially restored or marked as completed recovery. Those adapters remain required final lifecycle work.
