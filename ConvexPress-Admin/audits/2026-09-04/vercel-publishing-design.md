# Vercel publishing integration

Continue the approved provider-to-domain workflow with one provider project per independent website environment. A staging database uses its own Vercel project and stable production alias inside that project. No website shares a project or mutable runtime identity with another environment.

The control plane reserves account, project name, public ownership marker, instance, origins, artifact digest and a release receipt before writes. A database transaction records each project/deployment dispatch before its provider request. Lease expiry transfers observation rights, never permission to repeat an unconfirmed write. Recovery reads the exact project name plus creation-time ownership marker, or the exact deployment metadata receipt; absence after an uncertain dispatch remains pending. Confirmed provider rejection may be recorded separately, while successful-but-unacknowledged responses must reconcile. A new artifact cannot replace an ambiguous deployment.

Project creation includes a non-secret unique `CONVEXPRESS_HOSTING_TARGET` plain production environment variable. An existing unmarked or differently marked project is never adopted by name. This is the provider-side identity that survives a lost creation acknowledgement. Each deploy also binds receipt, artifact and instance in metadata and public runtime bindings. Provider ownership is rechecked around I/O; account revocation, scope moves and old lease tokens cannot advance control-plane state.

Desktop main reads a bundled, integrity-checked Build Output artifact and performs only content-addressed file uploads. Provider secrets stay out of renderer responses. The control plane owns project and deployment creation, receipt reconciliation and final runtime verification. The native panel reports the durable phase and can resume after restart. Cancellation stops further work but does not pretend a dispatched provider write was undone.

Completion requires a READY production deployment, assigned exact registered alias, project domain ownership/verification, and both real SSR routes returning the bound instance/release/artifact. Redirects are refused. Custom domain setup reports provider verification records and awaits actual propagation; it must not claim domain acceptance from deployment READY alone.

Implementation gates: runtime HTTP identity and artifact integrity; transactional contention/revocation/uncertain-write tests; desktop upload and cancellation integration; control-plane types/contracts; configured bundled SSR; real Electron-to-Vercel provisioning/publish/resume and served domain acceptance. Source checkpoints are not live provider proof.

API evidence reviewed September 5: [project creation](https://vercel.com/docs/rest-api/projects/create-a-new-project) supports creation-time environment variables. The official [Vercel client types](https://github.com/vercel/vercel/blob/main/packages/client/src/types.ts) and [deployment request](https://github.com/vercel/vercel/blob/main/packages/client/src/deploy.ts) include and forward deployment environment bindings even though the simplified REST documentation omits that option. Final provider acceptance still verifies the actual runtime.
