# Maintained media reverse index — implementation design

## Current evidence and exact boundaries

Deletion currently calls `media/references.findMediaReferencesForIds`, which iterates 26 generated owner tables. Scalar fields use existing generated indexes; arrays and opaque owners require complete table pages. `referenceScan.completeReferencePage` correctly accepts inert split cursors after root's live repair. Its limits will not be raised or reinterpreted. Storage ownership already uses independent indexes for primary media, sizes, and exact mediaMeta backup storage IDs; retain that path.

The guarded producer inventory is `media/referenceInventory.generated.ts` plus `referenceOwners.ts` / `referencePolicy.ts`. Current owners: appearance_drafts, commerce_product_categories, commerce_product_variants, commerce_products, fieldDefinitions, fieldValues, gallery_albumItems, gallery_albums, kb_articleVersions, kb_articles, kb_collections, kb_templates, layouts, lms_certificate_issues, lms_certificates, lms_courses, lms_lessonVersions, lms_nodes, postMeta, posts, recipes, reusableBlocks, revisions, settings, themes, users.

`attachmentGuard.ts` already wraps insert/patch/replace in 54 source files, but currently only validates references. `references.applyReferenceClear` writes/deletes owners directly. Promotion shared.write and rollback validate then write dynamically. Current direct owner deletes include posts/pages permanent deletion, revision retention, custom-field cleanup, reusable blocks, appearance drafts, gallery item replacement, product/variant/category deletion, profile deletion, KB cleanup, and LMS tree/course/certificate/seed cleanup. Direct owner inserts/patches also remain in fixed demo/setup/auth paths and ancillary settings writers; input-bearing ones must either use the hook or have an explicit source-checked no-reference proof before readiness can be claimed. Prior inventory documents are historical; implementation must inspect current calls, not assume their earlier unguarded status still holds.

## Invariants and bounded protocol

1. One edge row per media ID + owner document + active generation. Its payload retains the exact reference paths and opaque flags needed by existing force-clear adapters. Duplicate references within an owner do not create duplicate edge rows. Deletion queries only the selected media's generation index, then validates bounded current owner documents; it never scans the media library to discover references.
2. Insert/patch/replace validate the complete candidate and reconcile its edge set in the same transaction. Owner deletion removes edges in the same transaction. No context/database proxy. Forced clearing uses these same hooks. Removal of an attachment must remove its edge even when the old media is no longer attachable.
3. A bounded backfill walks one owner page per mutation using persisted cursors and split ranges. It never advances past SplitRequired data. Concurrent hooked writes maintain edges, and owner reads participate in the same transaction as indexing. Readiness requires every generated owner completed under the exact extraction/writer coverage version and deployment epoch. Unsupported oversized/opaque structures leave a visible blocked state, never a complete receipt.
4. Existing opaque/history policy remains conservative: exact typed IDs and literal/JSON media references in generated string/any roots retain media. Unknown encoded payloads are not declared supported; matched opaque references still refuse forced rewriting. Revisions and private drafts remain retention owners. Raw import cannot manufacture trusted readiness.
5. A readiness row alone cannot fence replaceAll restore: old ready rows would be restored too. Use a nonsecret out-of-snapshot deployment environment epoch, rotated and read back before every managed raw import/restore. A mismatched epoch or coverage version blocks index trust until backfill. Initially unconfigured installations may retain the existing complete bounded scan path; this is a safe migration fallback, not index completeness. Once indexed/epoch-configured, missing/stale/incomplete readiness fails closed.
6. Managed CP/native raw import paths need epoch rotation before dispatch, with uncertainty leaving the index unavailable. Arbitrary administration-key database writes remain a privileged boundary: application code cannot intercept them; operator tooling must invalidate/rotate before those writes. Do not claim the database itself enforces application hooks.
7. Static writer coverage checks must fail when a relevant raw writer or producer shape changes without review. The generated coverage fingerprint includes extraction/owner inventory and audited write boundaries, so old readiness cannot silently cover new schema paths or unsupported writers. New canonical writers will use the same hooks; auth owns their separate authoring-version permit/fence.
8. Shared storage ownership stays independently checked through current indexed storage owners. Removing a library edge is never permission to delete shared raw bytes.

## Intended proof

Actual handler tests: large unrelated owner/library sets with one bounded matching edge; two owners/one media; removal and replacement; delete cleanup; atomic failure rollback; opaque and historical retention; force-clear; resumable page and split traversal; concurrent changes across cursor progress; missing/version/epoch/incomplete readiness refusal; restored ready rows with stale epoch refusal; mismatched/tampered owner evidence; shared-storage protection. Source contracts enumerate guarded and exempt writer sites; raw import tests assert epoch rotation precedes import and failure prevents dispatch. No live calls or deployment in this subtask.

## Dynamic writer and deployment coverage follow-up

After the literal/typed-owner conversions, the refreshed compiler-assisted inventory contains 220 potential-owner or untyped dynamic writes across 52 files. Most operate on orders, membership grants, subscription contracts, or other nonowner tables. Rather than freeze their current source text as unexplained exemptions, the proposed explicit dynamic patch/delete helpers resolve an ID against the generated owner-table inventory using `normalizeId` (no whole-table read). Actual owner writes then go through the existing attachment/canonical-format/edge hooks; nonowner records keep their ordinary DB operation. A supplied table hint must agree with the resolved identity. This remains explicit call-site integration, with no context proxy. The normal typed owner wrappers retain their exact table/argument contracts.

Known remaining owner-bearing dynamic paths include LMS course deletion and seed cleanup (certificate issues/nodes), WordPress `patchEntity` (currently swallows every write error), and dev-only purge. The WordPress helper must only tolerate a confirmed missing entity and propagate attachment/canonical-format refusals. Raw dev storage purges require explicit index invalidation before their destructive loops; they cannot imply complete reference knowledge. Management legacy-session deletion is a confirmed nonowner path.

Coverage checking must reject raw literal owner writes and unresolved dynamic DB writers outside the named central integration helpers, including common local DB aliases/member captures. Literal nonowner calls can be accepted against the current generated owner inventory. New media-bearing schema fields automatically make their table an owner and invalidate that exemption. The protocol version should hash extraction/inventory/backfill/hook semantics, not arbitrary line-number churn. A stale generated coverage file must fail the actual deployment preparation path, not only an optional local command.

The native portable runtime already stages TypeScript for CLI checks. Its preparation and deployment currently run extension generation and typechecking but do not execute media writer-coverage validation. Once implemented, the checker and its dependencies must be copied and invoked there and in the ordinary backend deployment script. All managed snapshot replacement reaches control-plane `operations/snapshotImportApi.ts`; that is the central external-epoch rotate/readback boundary. No distinct native raw import executor was found in the current source search.

## Implemented checkpoint

The maintained hooks, generated deployment coverage, bounded backfill/current-owner validation, managed restore epoch fence, dev-purge invalidation, obsolete-generation cleanup, and authorized Admin progress controls are now implemented and source-tested. See [media-reverse-index-outcome.md](./media-reverse-index-outcome.md) for exact evidence, deployment order, and remaining live acceptance. The initial false coverage constant described above has been replaced by generated source coverage plus explicit external-epoch/backfill readiness; an unconfigured deployment still uses the legacy bounded scanner.
