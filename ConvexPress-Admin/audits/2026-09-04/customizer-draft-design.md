# HB3 Customizer draft and promotion design — September 4, 2026

1. Keep `appearance.template` as the published section and existing readers compatible. A dedicated authenticated snapshot returns effective migrated values, an opaque SHA-256 revision of those values/document revision, and server-owned site identity. Publish validates the section and expected revision in one transaction; a changed revision is a conflict, never a silent overwrite. A live site (or a site without identity) requires explicit live confirmation.
2. Store per-user/per-pack drafts in an additive `appearance_drafts` table with source revision, complete module override snapshot, variants, and a draft revision. Draft saves are capability checked and compare their own expected draft revision to avoid multiple-window overwrite. Public settings never contain drafts. Published writes keep the migration receipt independent of values.
3. One pure history/reset/preset model lives in the Website SDK and is generated into the Admin mirror by `sync:templates`. A bounded undo history holds immutable override snapshots. Reset removes overrides, and Shop reset also removes associated surface variants. Brand reset removes brand-bound field overrides. A draft is a complete replacement of saved overrides, layered over brand/pack defaults for preview; absent fields truly reset.
4. Ship named color presets in each pack manifest; sync includes presets and defaults in the Admin summary. Applying a preset is one undoable operation. The Customizer offers group/brand reset, undo/redo, saved-draft recovery, and a changes review before Publish. An incoming server revision while the draft is dirty raises a conflict notice and offers explicit reload, preserving the draft until the operator chooses.
5. Promotion copies only reviewed published staging template settings. The standalone control shell identifies the same website's live instance; the existing control-plane session broker authorizes a short-lived live site session. Fetch a target snapshot for review, then write through the same revision-checked mutation, with source/target identity checks and explicit live confirmation. No deployment keys are exposed. Promotion does not clone content or any other settings section. Independent environments cannot share a database transaction: the reviewed staging snapshot is immutable for the operation and the live revision is checked atomically at commit.
6. Ordinary single-site publishing remains available; cross-environment promotion requires the standalone control context with a configured live connection. No speculative endpoint or credential is accepted from a form. All tests use local handlers/clients; root owns live/browser acceptance.
