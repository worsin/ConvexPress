# C01 scoped hosting accounts and cloud creation receipts

Hosting accounts belong to an organization and optionally a business. An organization account may serve its businesses; a business account is restricted to that business. Provider custody requires a current active agency owner or administrator plus `connection.manage`; customer/site grants do not confer custody. Website use additionally requires matching active hierarchy and `site.deploy`. Explicit denies still apply to administrators.

The connect action authorizes before provider HTTP, verifies the exact external account identity, then encrypts the token with the existing versioned AES-GCM envelope. AAD binds organization, business, provider and external account ID. A transaction repeats authorization and optimistic revision checks after HTTP. Public account lists contain metadata only. Revocation erases the envelope and keeps audit/resource metadata. Rotations verify a replacement token and require the previous account revision. Personal Vercel user IDs use the user endpoint; team IDs use the team endpoint.

Cloud operations declare a bounded step plan before remote mutation. A transaction claims each step once. Interrupted/uncertain intents return `reconcile`; confirmed steps return immutable provider IDs. Only explicit definitive provider rejections may enter `rejected`, which permits one subsequent creation attempt. Provider actions decide which HTTP responses are definitively rejected; network, parse and server uncertainty must remain reconciliation-only. Step attempts are counted. Completion requires every declared step confirmed.

A provider resource ownership index binds provider + external account ID + resource kind + external ID to one step/website. Production and staging share the deployment namespace, so they cannot reference the same database. This guard also spans separate hosting-account records that reference the same external provider account. Resource records remain after credential revocation.

The UI manages accounts at organization/business scope and exposes create/adopt on website pages only after agency role and scoped capability checks. Tokens are transient password input state, cleared on submit/cancel, and never saved to browser persistence. Durable receipts render project/environment IDs and recovery state. Adoption receipts use the agreed `Adopt project N` name to recover the explicit project ID after reload; normal retries retain the original receipt name if the website title changes.

Root owns actual provider adapters, creation/adoption actions, desktop deployment transport and live acceptance. This work does not add remote retries, delete provider resources, or assume successful creation means a website is initialized or published.
