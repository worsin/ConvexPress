# P1: Live promotion replaces operational data and imports source credentials

Confirmed by current source; no live promotion or snapshot copy executed.

The UI calls the operation “Promote into live” (`apps/web/src/control/components/LifecyclePanel.tsx:291`) but clone and promotion share `operations/actions.ts:395` → `importTargetBoundSnapshot` at line 317. Both archive preparers preserve only five management tables (`operations/snapshotRestoreArchive.ts:18`); the streaming path retains every other source entry (`operations/remoteSnapshotArchive.ts:527–558`). Import explicitly requests `mode: "replaceAll"` (`operations/snapshotImportApi.ts:197`). All paths in this paragraph are under `/Users/worsin/.codex/worktrees/convexpress-hardening/ConvexPress-Admin/`, with operations paths under `packages/control-plane/convex/`.

Consequences:

- Live users, roles, orders, memberships, enrollments/progress, form submissions, settings, API keys, local refresh tokens, and delivery queues are replaced by staging state. Target-only tables are not selected for preservation. This is full database replacement, not content promotion.
- `settings.general.siteUrl/homeUrl` and `settings.integrations.clerk` come from staging. The public Clerk configuration prefers stored settings (`packages/backend/convex/auth/clerkPublic.ts:50–74`) while deployed JWT trust still comes from target `CLERK_JWT_ISSUER_DOMAIN` (`auth.config.ts:49`). Independent Clerk applications therefore mismatch; copying customer rows does not transfer or correctly map Clerk identities into the target application.
- Encryption keys are independently generated once per deployment (`packages/desktop/electron/ipc/siteDeploy.ts:421`, `ipc/setup.ts:100`). Copied settings ciphertext is decrypted using target `SHIPPING_PROVIDER_ENCRYPTION_KEY` (`packages/backend/convex/helpers/settingsSecret.ts:25,78`), and webhook secrets use `WEBHOOK_SECRET_ENCRYPTION_KEY`. Snapshot transport neither copies environment variables nor re-encrypts these records. Independent keys cause authentication/decryption failures; sharing keys instead makes staging service credentials effective in production. Neither outcome preserves target integration boundaries.
- Source opaque local refresh credentials can cross into the target despite different JWT signing keys. `POST /auth/refresh` (`packages/backend/convex/http.ts:101`) reads the presented desktop header/cookie, hashes the raw token, looks up the copied refresh row, checks the copied active local user, rotates it, and signs a fresh **target-signed** access token (`auth/refresh.ts:49–116`). `refreshTokens` has no environment stamp (`schema/auth.ts:5`), and lookup/rotation only check hash/user/expiry (`auth/internals.ts:179–219`). Preconditions: attacker possesses a still-valid source refresh token for a copied local account permitted to log in, then presents it at the target endpoint from an accepted origin/header context. This does not require possession of the target signing key. Copying local password hashes also enables a separate source-password login path and remains part of the broader replacement policy.
- API bearer keys have the same issue: `packages/backend/convex/api/internals.ts:108–164` accepts a copied hash/scopes/status without binding the key to the target deployment. Imported queued email can also become eligible for the target's existing five-minute batch processor (`packages/backend/convex/crons.ts:58`). No automatic-delivery quiescence is part of archive preparation.

Existing safeguards are useful but insufficient: operator authorization, exact live confirmation, verified pre-backup/checksums/identity, retained target management authority, and cleared management sessions. Clearing management sessions does not clear `refreshTokens`, API credentials, customer data, or provider configuration.

Implementable correction:

1. Treat the existing transport as an explicit destructive full replacement/restore operation. Fail closed for `site.promote` until a promotion manifest exists; changing UI text alone is insufficient. Same-instance disaster restore may replace business data but must validate schema and encryption-key version, retain target environment authority/configuration, and quiesce outbound processors until reviewed resumption. Cross-environment full clone needs a separately defined operational-data and identity policy, not an implicit staging publish.
2. Content/template promotion must export an allowlisted, versioned dependency manifest: selected pages/posts/templates and explicitly selected catalog/course structures, their taxonomy/menu/media references, and approved nonsecret presentation settings. Default-deny unknown extension tables/fields. Preserve target users/auth/roles, customers/orders/transactions, membership grants/enrollments/progress, form responses, runtime queues, integrations/credentials, and origin settings. Resolve dependencies with stable content keys and durable source→target ID/storage mappings; do not overwrite whole tables or assume source Convex IDs already exist on target. Map author references to explicitly chosen target operators. Preserve member restriction policy while resolving target plan identities; never copy member grants as content.
3. Build a target-bound dry-run manifest with conflict/revision checks, exact changes and preserved areas; commit via idempotent bounded mutations and a durable receipt, with pre-backup and rollback. Block target writes that invalidate the approved manifest. Postchecks must prove production identity, Clerk application, origins, users/customer counts, credential decryptability, and no source refresh/API credential acceptance or queued delivery.
4. Independently stamp newly issued refresh/API credentials with deployment authority and reject unstamped/mismatched rows on every verification/rotation. Same-environment restored stamped records retain their binding. Old unstamped records cannot safely be adopted after a copy; require local re-login/API-key reissue. This bounded defense does not solve copied passwords, customer data, secrets, or the promotion design and must not be presented as doing so.

Acceptance must use different source/target Clerk apps, encryption keys, users, credentials, URLs and business rows. Test intentional same-environment restore separately from cross-environment content promotion and full clone. The session/API binding repair is separately authorized; archive and promotion implementation remain unchanged during this audit.
