# Legacy appearance migration design — September 4, 2026

Applies to HA2 palette preservation and HA3 Shop layouts consolidation. This is a staged per-site migration; source records and schema stay readable until the migration has actually run on each site.

1. One pure projection merges raw `appearance.template`, the stored `commerce.layout` row (if present), and the active legacy theme palette. Existing explicit template variants and per-pack settings win. The active pack defaults to `core` only when no pack is selected. Other packs, other modules, surface overrides, custom color tokens and dark-prefixed tokens are preserved.
2. Map legacy `shopLayout` → `variants["shop.catalog"]` and the active pack's `shop.catalogVariant`; `productLayout` → `variants["shop.product"]` and `shop.productVariant`; `cartPanel` and `gridDensity` → the active pack's Shop module. Existing effective template variant wins when seeding a missing Shop field.
3. Map palette entries `{slug,color}` from `activeTheme.globalStyles.settings.color.palette`, falling back to `activeTheme.colorPalette`, into active-pack `colors[slug]`. Copy only into null/absent values. Validate token slugs and keep dark/custom tokens. The content agent owns the SDK renderer compatibility for those tokens.
4. Both authenticated Appearance settings reads and public template projection use this helper until persistence. This prevents layout/palette changes between installing code and running a migration. Legacy `layoutConfig` remains an explicitly derived compatibility response for older storefront builds; new `useShopLayout` consumes the template config and active Customizer draft.
5. One capability-checked migration mutation persists the projected template settings and an optional receipt on the settings document in the same transaction. The receipt disables future legacy fallback, so reset-to-default and switching templates do not reintroduce old settings. A second invocation performs no writes. Template settings updates first persist the migration; the incoming explicit update is then applied. Original theme/layout records are retained as rollback evidence until per-site live migration/visual acceptance.
6. Retire the Settings › Shop layouts editor to a redirect to Appearance › Customize and remove its duplicate navigation entry. Add grid-density controls to the Shop settings module, retaining defaults and legacy preview URL behavior.

Verification: actual-handler tests for anonymous denial, absent template row, existing per-pack override preservation, dark/custom palette preservation, migration-before-update, no-write repeated migration, post-migration reset not resurrecting legacy values; pure layout resolver tests for active-pack/draft/preview precedence. Backend and both web typechecks, template catalog checks, and targeted unit tests. No deployment/provider/browser mutation in this task.
