## 3. Findings

Severity is about risk to *this* delivery. I mark each **Defect** (wrong code/config today) or **Gap** (correct but unproven/unbuilt) per Codex's request.

### F1 — Plugin default-enablement disagrees between Website manifests and backend registry · **HIGH · Defect**

Two independent sources of truth decide whether an extension is on, and for four extensions they disagree.

- Backend: `ConvexPress-Admin/packages/backend/convex/plugins/registry.ts` → hand-written `PLUGIN_DEFAULTS`.
- Website: `apps/web/src/extensions/*/manifest.ts` → `defaultEnabled`, read via `extensions/sdk/registry-core.ts:extensionEnabled`.

Both use identical fallback semantics — a stored boolean wins, otherwise the side's own default:

| Extension | Backend default | Website manifest default |
|---|---|---|
| `gallery` | `true` | **`false`** |
| `knowledgeBase` | `true` | **`false`** |
| `tickets` | `true` | **`false`** |
| `recipes` | `true` | **`false`** |
| `customFields` | `true` | **no manifest at all** |

So on any site whose `plugins` settings section lacks those keys — a fresh install, or a site where the toggle was never touched — the backend resolver treats the extension as **enabled** while the public Website gate treats it as **disabled**.

Why this matters now, not later: the four mismatched extensions own **exactly four of the 13 pending Plugin-category blocks** — `gallery/album`, `support/kb-search`, `support/ticket-cta`, `recipes/recipe-card`. The failure signature is "block renders empty / is hidden although its data resolves", which is the hardest class of bug to attribute mid-batch, and it lands squarely in Task 3. Nothing cross-checks the two tables: `predeploy` regenerates `_pluginIndex.generated.ts` but no script compares backend defaults against Website manifests.

**Recommendation.** Before the Task 3 plugin batch: pick one authority (the manifests are the better one — the Website side is already fully manifest-driven via `isPublicPluginEnabled`), make the backend derive from it, and add a `--check` that fails when the two disagree. Under the plan's §2 procedure this is a legitimate bounded dependency repair: required workflow = plugin-block data/visibility; exit check = both gates agree for all 17 ids. It is a small change that de-risks up to 27 pending blocks.

### F2 — A Stop hook auto-commits and pushes, contradicting "No push" · **HIGH · Defect**

`.codex/hooks.json` registers a `Stop` hook running `.codex/hooks/auto-push.sh`, which on every turn that touched files does `git add -A` → `git commit -m "auto: <ts>"` → **`git push origin HEAD`**, swallowing all failures (`|| true`).

This contradicts explicit instruction in both controlling documents: plan §1 *"Do not push without separate authorization"*; handoff *"No push."* (stated twice). It has already had a visible effect — the handoff document says it is *"deliberately uncommitted… Do not mistake it for an unrelated user edit"*, yet the hook committed it as `7f8b6399` about a minute after it was written. There are **216** `auto:` commits in history.

Current blast radius is limited but latent: `main` is **142 commits ahead** of `origin/main`, whose tip is `5a4d604e` from 2026-09-03 — so pushes are not currently landing (the hook hides the reason). `gh` is authenticated as `worsin`, which does match `github.com/worsin/ConvexPress`. If git credentials ever resolve for that remote, one hook firing publishes 142 unreviewed commits.

**Recommendation.** Owner decision, not Codex's: either drop the `git push` line from `auto-push.sh` for the duration of this delivery (keeping the local auto-commit, which is genuinely useful), or disable the hook. Also note the script's own header says *"every Claude turn"* — it was authored 2026-04-27 for a Claude session and is now wired into `.codex/hooks.json`, so it fires for Codex too. I have not modified it; changing a git-push hook is the owner's call.

### F3 — The status file is a scaffold, not yet a tracker · **MEDIUM · Gap**

That single pass converts 79 vague rows into a schedulable queue, and it is also the artifact that lets these audits check progress objectively.

## 4. Assessment of the plan itself

Codex asked whether proposed work closes actual deliverables. My read: **the plan is unusually good and I would not restructure it.** Specifically strong —

- It defines completion as a usable delivery and explicitly forbids inferring completion from renderer counts, file counts or green logs (§1, and repeated in the handoff). That is the correct guard for this codebase, where counts are abundant and flattering.
- The five-line blocker gate (§2) is the right mechanism for a project whose last month drifted into a whole-app audit, and the worked examples ("do not redesign all refund accounting") are concrete enough to actually bind.
- The five-way classification (§3) and "do not reset all accepted blocks to zero after a shared change" protect the 58 verified rows from being churned — genuinely valuable, since re-earning that evidence would cost days.
- §5's file-ownership table is accurate. I verified every path resolves.
- Task 2's batching (several related blocks on one authored page, one save/reopen, shared deployment and cleanup) is the correct amortisation and directly addresses the cost problem the previous session ran into.

Two things I would add, both cheap:

1. **A shared-gating pre-flight before Task 3** (F1). One consistency check ahead of the plugin/commerce batches, rather than debugging the same disagreement inside four separate block batches.
2. **Make the populated status file Task 1's exit criterion** (F3). The plan already says status lives there; saying it must be *populated* before Task 2 opens gives Task 1 a verifiable end and gives these audits something objective to measure.

On the cost/efficiency question the plan raises implicitly: the previous session spent 3.497 B tokens and 11.93 M output tokens over 24 days to reach 58/137 with the presentational half done. The remaining 79 are individually harder (data, auth, actions) but far more *shareable* — 45 of them sit behind 33 resolvers and one gating mechanism. If batching works as designed, the second half should not cost proportionally what the first did. That is the main thing I will track hour over hour.
