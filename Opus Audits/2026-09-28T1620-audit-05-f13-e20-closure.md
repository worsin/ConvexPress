## 3. F13 closed — and Codex's adaptation was right

I recommended routing conflicts into `load()` so the existing Restore/Discard offer would appear. Codex accepted the finding, **declined that specific fix**, and explained why: blindly calling `load()` on a saved-revision `CONFLICT` can approve an unchanged private generation while the editor still holds an obsolete document base, producing a repeat-conflict loop. That is a real flaw in my proposal and I withdraw it.

What shipped in `29632560` is a three-way split, verified in the diff:

- **`DRAFT_CONFLICT` → `return load()`.** Competing generations now auto-reconcile into the `offered` choice. This is the half of my recommendation that was sound.
- **`CONFLICT` → new `"revision-conflict"` status**, recording `rejectedRevision.current = attempt.baseRevision`. It deliberately does *not* read. The effect re-arms only when `session.base.revision > rejectedRevision.current` — i.e. after a genuine Save receipt or explicit resolution advances the accepted revision. `load()` also gained a top guard returning early while `rejectedRevision` is set and the base has not advanced, which is the "without stale retries" in the commit title.
- **Unknown / transport errors → `"error"`** with the existing manual Retry. Correct: an uncertain acknowledgement must not auto-retry.

The code discrimination is sound — `error.data.code` is read only when `data` is an object carrying `code`, so plain diagnostic text is not mistaken for a structured conflict, matching how `drafts.ts:refuse()` throws `new ConvexError({ code, message })`.

Two details worth crediting because they address the failure modes I listed rather than only the symptom:

- **The new state is surfaced calmly.** `CanonicalEditor.tsx:613` renders it with `role="status"`, not `role="alert"`: *"Site autosave is paused while the saved revision is resolved. Your edits remain in this window."* That fixes the specific problem I reported — a benign interleaving no longer produces an alarming "autosave is unavailable" alert.
- **`locked` no longer deadlocks simultaneous conflicts.** It is now `!session.conflict && (loading || revision-conflict || offered)`, with the reason in-comment: an accepted-document conflict must stay resolvable before the private draft is reviewed. Without that, the two conflict UIs could mutually disable each other — a failure mode I did not anticipate.

All three consequences I reported are resolved: no misleading alert, automatic recovery for competing generations, and the reconciliation UI reachable without manual Retry. **F13 closed.**

Codex is explicit that the in-flight Save overlap is *controlled regression evidence, not a native timing claim*. That distinction is the right one to keep, and I have not independently executed any of it — see §6.

### F14 — Visual correctness masked a real defect; make console-clean an explicit per-row criterion · **LOW · Process recommendation**

The genuinely instructive part of this batch is the regression Codex found while accepting it. A newly nested Suspense boundary retried a seed-data grant *after* the parent installation effect had revoked it. Codex's own description of the symptom is the lesson: all **8 public cases rendered the expected content and chunks but emitted React hydration errors**, so it refused to accept them, moved the loading boundary above grant installation, preloaded exactly the SSR-marked definitions, and re-ran to 16 clean cases across 4 packs and 2 widths.

That is exactly the right call, and it is worth generalising because **74 rows remain**. A screenshot that looks right and a DOM that contains the right text are not sufficient evidence — this batch is the proof, since both were satisfied while a real ordering defect was live.

The plan does not currently state this. Grepping `2026-09-28-editor-template-delivery.md` for console/hydration/page-error language finds only **E05**, scoped to preview protocol and readiness boundaries — not a general per-row acceptance requirement. The precedent does exist upstream: `HANDOFF-ASTRA-2026-09-04.md:8` records the original template evidence as *"Screenshots of every key page, zero console errors."*

**Recommendation:** state "no console errors, including hydration warnings" as an explicit per-row acceptance condition in Task 2/3, since Codex is already practising it and the standard is inherited from the handoff. Cheap to write down, and it prevents a later batch from accepting a visually-correct row with a dirty console. Not a defect in delivered code — a gap between practice and specification.

### F15 — The main-entry size gate fails, and I could not locate its threshold · **INFO**

Codex reports the main-entry budget failing at **309.29 KiB against 292.97 KiB**, and that the pre-change build already exceeded its limit at **313.71 KB against 300 KB**. Two observations:

1. **The failure predates E20 and the lazy work improved it.** 313.71 → 309.29 on the entry. So this is a pre-existing Task 8 delivery gate, not a regression introduced by per-block lazy loading, and Codex is right to say it is not claiming global green.
2. **I could not find the gate's configuration.** I searched `ConvexPress-Website` for `chunkSizeWarningLimit`, `entryLimit`, `MAX_ENTRY`, `size-limit`, and the literal figures `292.97` / `309.29`; every hit was unrelated form-entry-limit code. So the threshold is not discoverable in the Website workspace — it may live on the Admin side or come from the build tool's own reporting.

Not a defect, and I am not asserting the gate does not exist — only that I could not verify its threshold independently. Worth recording where it is configured when E22/Task 8 is addressed, because a delivery gate whose limit cannot be located is one nobody can be held to, and the two differing limits quoted (300 KB vs 292.97 KiB) suggest at least a unit ambiguity.
